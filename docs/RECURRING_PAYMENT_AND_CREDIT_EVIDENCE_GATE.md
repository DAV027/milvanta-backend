# Date-specific credit provenance and signed capture observations

**Release status: DRAFT / DISABLED / NOT FOR CUSTOMER PAYOUTS**

## Evidence produced by this branch

Migration 024 creates `subscription_billing_credit_provenance`, linking each credited or reversed morning to a single `subscription_billing_adjustments.id`, a source type/event identifier, an exact `delivery_date`, and its signed day and paise amounts. It does not create any new credit or change the existing billing adjustment arithmetic.

The existing subscription service can write provenance inside the **same existing PostgreSQL transaction** as a new adjustment for skip, unskip, vacation, and indefinite-pause resume. This is an **optional evidence-only feature**; `RECURRING_CREDIT_PROVENANCE_ENABLED` defaults OFF. An exception rolls back both the original operation and its evidence rows; duplicate evidence for an adjustment/date fails closed rather than silently generating duplicate credit records. Existing legacy adjustments are **not backfilled** from free-form notes.

All new rows have `evidence_state='date_known_payment_unverified'`, and `payment_id` and `billing_cycle_reference` are intentionally NULL. Even when a subscription notes field contains a payment ID, that does **not** establish which captured invoice or cycle paid for an adjusted morning. Never present these records as approved compensation.

Migration 025 creates `recurring_subscription_capture_observations`, an append-only evidence table with a globally unique gateway payment ID and webhook event ID. A new helper in the already signature-verified webhook transaction records a **raw** `status=captured`, `currency=INR` payment entity only if its subscription ID matches an explicitly live-mode subscription, the amount is a positive integer, and the paid-cycle number is valid. Invoice-only and separately fetched payment-list evidence are excluded. The helper is **OFF by default** unless `RECURRING_CAPTURE_OBSERVATIONS_ENABLED=true`.

This is evidence of what an authenticated webhook reported, **not independent Razorpay settlement confirmation**, not authorization to transfer funds, and not proof that every installment was collected. It makes no Razorpay API calls, refunds, charges, renewals, notifications or deliveries.

## Read-only reconciliation

The internal `src/services/recurringFinanceReconciliation.js` report now separately exposes:

- Net existing credit adjustments and the exact-date evidence that explains them, with a flag if any legacy adjustment lacks source rows
- Dates where two independent positive credit sources claim the same morning, even when later unskip reversals net the amount down
- Count, observed amount, and cycle numbers of unique, signed-webhook payment observations; no assumption that nominal `total_amount_paise` equals captured cash
- Obligations or credit claims with no signed payment observation, foreign or conflicting payment identities, repeated captures in a cycle, outstanding reservations and refund/fulfillment discrepancies

**Report permissions are always false:** `customerPayableCreditPaise=null`, `customerRefundableAmountPaise=null`, `mayAutoApplyCredits=false`, `mayAutoRefund=false`, `mayAutoGenerateDeliveries=false`.
