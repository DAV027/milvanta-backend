# Milvanta — independent Razorpay snapshot reconciliation gate

**Status: DRAFT / INTERNAL READ-ONLY / NO GATEWAY CONNECTION / NO FINANCIAL AUTHORIZATION**

The internal `src/services/recurringGatewaySnapshotReconciliation.js` performs offline comparison between **separately obtained Razorpay read-only API evidence** and local signed-webhook capture observations/refund requests. It **does not connect to Razorpay**, authenticate the supplied snapshot, fetch credentials, create charge/refund requests, mark bank settlement complete, or update any customer data.

## Inputs and evidence ownership

An authorized finance reviewer must separately verify that the Razorpay records were fetched from the **correct live merchant account**, with complete pagination and a known retrieval timestamp. Never paste API key secrets, payment-card details, contact data, or full customer information into repository tests or PR comments.

Inputs follow Razorpay entity fields:
- `payments[]`: `id`, `subscription_id`, `invoice_id`, `status`, `captured`, `amount`, `currency`, `amount_refunded`.
- `invoices[]`: `id`, `subscription_id`, `payment_id`, `status`, `billing_start`, `billing_end`. A missing paid invoice/cycle reference is **unverified**, never inferred from the contract amount.
- `refunds[]`: `id`, `payment_id`, `status`, `amount`, `currency`.
- `accountMode`, `subscriptionId`, `retrievedAt`, and explicit `complete` describe the reviewer-supplied snapshot; the module cannot authenticate those assertions.

The captured amount is the **sum of individual captured INR payment entities** (including previously captured-but-refunded payment entities only when `captured=true`); it is never `customer_subscriptions.total_amount_paise`. Payment `amount_refunded` is cross-checked against individually **processed** refund entities. Pending/created/processing refunds are separately reported as unfinalized, not counted as processed cash. Failed/reversed statuses do not count as processed.

A signed-webhook capture observation must match exactly on payment ID, amount, and subscription; a local processed refund must match the independently supplied refund ID, payment ID, status, and amount. Multiple payments per invoice billing interval, overlapping invoice cycles, missing receipts, foreign subscriptions, inconsistent currency, partial API pagination, or snapshot deficiencies are flagged.

## Output contract

The report always gives `status='manual_reconciliation_required'`, `independentlyConfirmedSettlement=false`, and no customer-payable/refundable amount. `mayAutoApplyCredits`, `mayAutoRefund` and `mayAutoGenerateDeliveries` are always **false**, including when all supplied records agree.

- `assessRecurringGatewaySnapshot` compares pure in-memory records and has no external or database access.
- `previewRecurringGatewaySnapshotReconciliation` loads only a subscription's locally saved capture observations and refund requests in one `REPEATABLE READ READ ONLY` PostgreSQL transaction, then compares them with the supplied snapshot.
- Neither function is exposed through Milvanta HTTP, admin, webhook, or cron routes.

**This is not independent bank settlement verification** and is not a substitute for reviewing Razorpay settlements, chargebacks, merchant terms, or actual final refund completion. The caller must establish external-source authenticity and completeness; this code does not.

## Release and policy blockers

1. Authorized merchant finance reviewer must independently authenticate live Razorpay API source and complete invoice/payment/refund pagination; identify the exact merchant account without committing secrets.
2. Verify all expected first and subsequent cycle invoices, their time ranges, capture evidence, settlement/chargeback status and any refund reversals. Do not infer missing cycles or prorate 2–12 month subscriptions from nominal plan totals.
3. Match dated skip, vacation, unskip and pause-resume provenance to **uniquely compensated delivery dates**, then reconcile them with outstanding first-cycle owed mornings and actual delivered orders; never issue compensation twice.
4. Resolve credits carried through recurring renewals and explicit cancellation terms; design real operator signoff and rollback.
5. Production deployment requires explicit release approval, workspace identification, independent tests, disabled-by-default switches, and migration review. Draft PR #37 must not be merged before these gates.
